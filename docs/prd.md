# 第1章 PoC目标与核心假设

## 1.1 一句话产品定义

一个由大模型驱动的对话式测评工具：候选人通过与大模型对话和实操完成测评，大模型分析全过程日志并输出AI素质等级判定；对高阶候选人，面试官现场提问后将文字记录录入系统，由大模型综合出终判。

## 1.2 本阶段目标

**不是**交付一个可用于日常招聘的产品，**而是**验证：我们设计的测评形式与题目思路，能否让大模型对候选人的AI素质做出与真人面试官基本一致的判断。

## 1.3 核心假设

| # | 假设 | 验证方式 |
|---|------|---------|
| **H1** | 对话式测评能采集到足够的、有区分度的行为信息 | 不同水平候选人的日志差异是否明显；大模型能否基于日志给出带证据的判定 |
| **H2** | 大模型的等级判定与面试官独立判断基本一致 | 三方对比数据（见1.5）的一致率 |
| **H3** | "工具模式"能观测到候选人真实的AI使用行为，而非表演 | 工具模式行为与面试官对候选人日常表现的了解是否吻合 |
| **H4** | 高阶候选人的"面试文字记录 → 大模型评估"路径可行且有效 | 终判与面试官判断的一致率；面试官环节是否带来判定变化 |

## 1.4 本期明确不做

| 类别 | 不做的内容 |
|------|-----------|
| 通知与触达 | 邮件发送、短信发送、站内提醒、催办 |
| 候选人管理 | 批量导入、进度追踪、标签分组、搜索筛选 |
| 报告 | 报告导出、PDF生成、候选人版报告 |
| 题库 | 题库管理界面、题目审核流、版本管理、题目分析看板 |
| 配置 | 多岗位方案、多套试卷、评分权重可视化配置 |
| 账号 | 权限体系、组织架构、SSO（面试官账号由后台直接创建） |
| 技术 | 防作弊检测、断点续答、并发优化、ASR语音转写、音频上传 |
| 集成 | ATS对接、任何外部系统API |
| 评分 | 大模型与面试官评分的加权合成（本期并列展示，不合成） |

## 1.5 PoC的核心实验设计：三方对比

对每一位进入面试官环节的候选人，系统必须记录三份独立判定：

| 代号 | 判定来源 | 输入信息 | 产出时机 |
|------|---------|---------|---------|
| **A** | 大模型初判 | 选择题 + 考官模式对话 + 工具模式日志 | 候选人提交后立即产出 |
| **B** | 面试官独立判断 | 候选人原始日志 + 追问题纲 + 现场提问所得 | 面试官现场提问后，**看到A和C之前** |
| **C** | 大模型终判 | A的全部输入 + 面试记录文字 | 面试官提交B之后产出 |

**强制约束**：系统必须在面试官提交B之前，完全隐藏A和C的等级结论。这是本PoC最重要的实验控制，一旦破坏，H2和H4的数据全部作废。

**A/B/C 三方对比要回答的问题**：
- A vs B：大模型不借助面试官，判断准不准（H2）
- A vs C：面试官环节带来了多少判定变化（即"面试官环节的增量价值"）
- B vs C：加入面试记录后，大模型能否追上面试官的判断（H4）

## 1.6 术语表

| 术语 | 定义 |
|------|------|
| **考官模式** | 对话框中大模型扮演提问者，负责提问与追问 |
| **工具模式** | 对话框中大模型扮演普通AI助手，不提问、不引导、不评价，供候选人完成实操任务 |
| **阶段目标** | 考官模式每个阶段要采集到的信息目标（替代传统"题目"概念） |
| **L0–L4** | AI素质等级，定义见4.4 |
| **个人深度轨道** | 以个人AI应用深度为主的能力发展方向 |
| **团队负责人轨道** | 以推动他人/团队使用AI为主的能力发展方向 |
| **自述实测落差** | 选择题自述水平与对话实测表现的差距 |
| **安全红线** | 触发即单独标记、不进入常规等级判定的严重问题 |
| **A/B/C判定** | 见1.5 |

# 第2章 产品形态与核心设计

## 2.1 设计理念

传统测评是"出题—答题—判分"。本产品改为"对话—观察—推断"：

- **不预设固定题目**，只预设"这个阶段要搞清楚什么"，由大模型自主组织提问
- **不设标准答案**，由大模型从全过程行为中提取证据
- **不靠自述评分**，自述只作为追问线索，用现场行为验证

## 2.2 两种模式的严格区分（开发重点）

这是全系统最容易做错、也最影响验证效果的设计点。

| 维度 | 考官模式 | 工具模式 |
|------|---------|---------|
| 大模型身份 | 测评对话助手（公开告知候选人） | 普通AI助手 |
| 候选人认知 | 我在被提问 | 我在用AI干活 |
| 测什么 | 认知、经历真实性、判断力、核验意识 | 提示词能力、迭代深度、任务拆解 |
| 上下文 | 携带选择题结果 + 本阶段目标 + 本阶段对话历史 | **完全干净，不携带任何前序信息** |
| 大模型行为 | 主动提问、追问细节、要求举例 | 只响应，不追问，不引导，不评价 |

**为什么上下文必须隔离**：如果工具模式携带了考官模式的历史，大模型会"知道这是考试"，从而主动帮候选人补全需求、提示他优化提示词，直接污染H3的观测结果。

**实现要求**：

1. 两种模式使用**独立的会话上下文**，工具模式初始化时上下文为空（仅含工具模式System Prompt + 任务描述）
2. 模式切换时，对话框内插入**系统级提示卡片**（视觉上与AI消息明显区分），文案：

> **进入实操环节**
> 接下来的环节中，这个对话框是一个普通的AI助手，它不会再向你提问，也不会评价你的操作。
> 请像平时工作中使用AI一样使用它，完成下面的任务。
> 任务：（任务描述）
> 时长：本环节 X 分钟

3. 界面顶部持续显示模式标识（考官模式："测评对话" / 工具模式："AI助手（实操中）"）
4. 工具模式下，大模型的行为禁令必须写死在System Prompt中（见5.2）

## 2.3 三段式测评流程

```
┌─────────────────────────────────────────────────┐
│  候选人环节（无人工介入，约30分钟）              │
├─────────────────────────────────────────────────┤
│  第0段  习惯选择题（5题，约2分钟）              │
│         ↓ 结果注入后续阶段作为追问种子           │
│  第1段  考官模式对话（10–15分钟）               │
│         S1.1 开场校验 → S1.2 核验意识           │
│                        → S1.3 深度探测（条件触发）│
│         ↓                                        │
│  第2段  工具模式实操（1–2任务，10–15分钟）      │
│         ↓                                        │
│  【大模型评估】产出 A：初判                      │
└─────────────────────────────────────────────────┘
                    ↓
          触发条件判断（见4.5）
          ┌──────────┴──────────┐
     不触发                   触发
        ↓                       ↓
   状态：已完成          ┌─────────────────────────┐
   （L2及以下）          │ 面试官环节（20–30分钟） │
                        ├─────────────────────────┤
                        │ 面试官查看追问题纲       │
                        │ （不含A的等级结论）      │
                        │  ↓ 现场提问              │
                        │ 粘贴面试文字记录         │
                        │  ↓                       │
                        │ 提交 B：独立判断         │
                        │  ↓                       │
                        │ 【大模型评估】产出 C     │
                        │  ↓                       │
                        │ 展示 A / B / C 三方对比  │
                        └─────────────────────────┘
```

## 2.4 大模型的四个职责与边界

| 职责 | 输入 | 输出 | 硬约束 |
|------|------|------|--------|
| **考官** | 当前阶段目标 + 选择题结果 + 本阶段对话历史 | 下一个问题或追问 | 不得泄露评分标准；不得评价好坏；不得决定阶段推进 |
| **工具** | 候选人提示词（干净上下文） | 普通AI助手回复 | 不得提问；不得引导；不得暗示这是测评 |
| **评估者** | 完整结构化日志 | 结构化JSON（维度证据+等级+置信度） | 每个结论必须附原话引用；无证据不得下结论 |
| **题纲生成者** | 候选人前两段日志 | 3–5个追问点 | 必须引用原话；**不得包含等级结论或评分倾向** |

## 2.5 一个必须写死的架构约束：阶段推进由后端控制

**大模型不决定流程走向。**

- 大模型只做一件事：在"当前阶段目标"下生成下一个问题
- 何时进入下一阶段，由后端状态机按规则判断（轮次上限 / 时长上限 / 信息充分度信号）
- 每轮结束后，后端要求大模型额外输出一个轻量信号（见5.1），但**是否推进的决策权在后端**

**理由**：若交给大模型自主推进，PoC阶段会出现流程失控，且每个候选人经历的流程不一致，破坏样本可比性。

## 2.6 选择题的定位

选择题**不直接参与评分**，只承担两个作用：

1. **追问种子**：候选人选"每天多次使用"，考官模式即针对性追问"今天用AI做了什么，具体说说"
2. **一致性校验信号**：自述高 + 实测低 = 落差信号，交由大模型识别为"倾向夸大"或"缺乏自我认知"，作为独立判断依据

## 2.7 已知局限（写入文档，不在本期解决）

| 局限 | 本期处理方式 |
|------|-------------|
| 候选人可另开窗口用外部AI辅助 | 不做技术防护；在评估Prompt中要求大模型关注异常信号（响应间隔过短、提示词风格与对话风格不一致、表达过于工整） |
| 工具模式任务通用，与具体岗位不完全贴合 | 本期接受，换取样本可比性 |
| 面试文字记录质量依赖面试官 | 提供录入规范提示；不做校验 |
| 样本量小（12–15人），统计意义有限 | 本期以定性判断为主，重点看失败案例 |

# 第3章 用户故事与场景

本系统仅两个角色：**候选人**、**面试官**。其余职责全部由系统承担。

| 角色 | 在系统中的动作 |
|------|--------------|
| 候选人 | 打开链接 → 填姓名 → 答选择题 → 对话 → 实操 → 提交 |
| 面试官 | 新建测评 → 复制链接（自行发出）→ 查看结果 → 对高阶候选人现场提问、录入记录、提交独立判断 → 查看三方对比 |

---

## 场景1：候选人小王完成测评（L2典型路径，不触发面试官环节）

> 小王应聘运营岗，收到面试官从微信发来的一个链接。
>
> 点开后是一个简洁页面："本次测评约30分钟，包含5道选择题、一段对话交流和1个实操任务。请在不受打扰的环境中完成。"他填了姓名"王磊"，点击开始。
>
> **选择题环节**：5道题在一页里。他选了"每天使用多次"、"付费订阅了1个AI工具"、"做过提示词模板但只自己用"、"同事偶尔会来问我"、"上周因为AI给的数据不对返工过"。提交。
>
> **对话环节**：页面切换成对话界面，顶部标着"测评对话"。AI开口："你好王磊，接下来我会和你聊一聊你平时使用AI的情况。你提到每天会用多次AI，能说说今天用AI做了什么吗？"
>
> 小王答："今天用AI写了一版活动推文。"
>
> AI追问："能具体说说你是怎么让它写的吗？你给了它哪些信息？"
>
> 小王答："我把活动的时间、优惠力度、目标人群发给它，让它写三个版本的推文，风格分别是活泼、专业、煽动性一点的。"
>
> AI追问："三个版本出来后你是直接用了，还是做了修改？"
>
> 小王答："改了。它写的活泼版有点太夸张，我让它把感叹号去掉，语气收一点，然后自己又调了两句。"
>
> 对话继续，AI问到了"上周返工"那件事："你提到上周因为AI给的数据不对返工了，能说说当时是怎么发现的吗？"
>
> 小王答："它给我一个行业渗透率的数字，我觉得偏高，去查了原始报告，发现它把两个年份搞混了。"
>
> AI又追问了两轮：他是每次都会查，还是只有觉得不对才查；有没有形成什么习惯。小王承认主要是"觉得数字不对才查"。
>
> 大约12分钟后，对话环节结束。
>
> **实操环节**：对话框里出现一张明显不同样式的卡片：
>
> > **进入实操环节**
> > 接下来的环节中，这个对话框是一个普通的AI助手，它不会再向你提问，也不会评价你的操作。请像平时工作中使用AI一样使用它，完成下面的任务。
> > **任务**：一位合作了两年的供应商，已经逾期30天未交付约定的物料，且前两次沟通都只回复"在处理"。请你完成一封发给对方负责人的邮件，目标是既要施加压力推动交付，又要保留后续合作的可能。
> > **时长**：本环节 12 分钟
>
> 小王在输入框里写："帮我写一封催供应商交货的邮件，语气要强硬一点但不要撕破脸。"
>
> AI给了一封邮件。小王看完觉得太客气，输入："语气再硬一点，明确提到已经逾期30天，而且前两次沟通对方都只说在处理没有实质进展。另外加一句如果本周内没有明确交付时间，我们会启动备选方案。"
>
> AI改了一版。小王又输入："结尾那句'期待继续合作'太软了，改成表达我们珍视两年合作、但也需要对方给出实际行动的意思。"
>
> AI给出第三版，小王觉得可以了，点击"完成本环节"。
>
> **结束页**："感谢参与本次测评，结果将由面试团队查看。"
>
> 后台：大模型分析全部日志，判定小王为 **L2 / 个人深度轨道**，置信度0.82，未触发面试官环节。面试官在列表页看到这条记录状态为"已完成"。

**对应用户故事**：

- 作为候选人，我希望**一开始就知道要花多久、有几个环节**，因为我需要安排时间，不想中途被打断
- 作为候选人，我希望**清楚知道什么时候是被提问、什么时候是我在用AI干活**，因为这两件事我的做法完全不同
- 作为候选人，我希望**实操环节的AI就是个正常的AI**，因为如果它一直提示我"你可以补充更多背景"，我就不知道该按平时习惯做还是按它的引导做
- 作为候选人，我希望**每个环节有明确的剩余时间**，因为我需要判断还能不能再改一版
- 作为候选人，我希望**提交后知道接下来会发生什么**，因为不确定感很糟糕

## 场景2：候选人小陈触发面试官环节（L3路径，含三方对比）

> 小陈应聘运营主管。前面的选择题和实操环节流程与小王相同，但在考官模式对话中出现了分叉。
>
> AI问她"今天用AI做了什么"，她提到自己把周报的数据整理环节整个改掉了：
>
> "我们以前每周要三个人各自整理自己模块的数据，再汇总，大概要花一天。我做了一套东西，把三个人的原始数据表格式统一，然后用固定的提示词让AI出初稿分析，现在半天就能出来，而且格式稳定了。"
>
> 系统的深度探测阶段（S1.3）被触发。AI追问了5轮：这套东西具体是什么形式；提示词迭代了几次、每次改了什么；除了她自己还有谁在用；有没有失败过。
>
> 小陈提到"迭代了大概三四次"、"另外两个同事现在也在用"、"有一次AI把两个月份的数据混了，后来我在提示词里加了强制标注月份的要求"。
>
> 实操环节表现也较好：她在第一条提示词里就给了完整背景（合作年限、逾期天数、前两次沟通情况、目标），后续做了两轮针对性修改。
>
> **大模型初判（A）**：L3 / 个人深度轨道，置信度0.68。判定理由中标注了"流程级改造与他人采纳的证据均来自候选人自述，需现场验证具体细节"。
>
> **结束页**（与小王不同）："感谢参与本次测评。你的部分回答需要进一步交流，面试团队会与你联系。"
>
> ---
>
> **面试官侧**：老张在测评列表页看到小陈这条记录，状态为 **"待现场验证"**。点开后看到：
>
> - 小陈的完整对话日志和实操记录（可展开阅读）
> - 系统生成的**追问题纲**（不含任何等级结论）：
>
> | # | 追问点 | 想验证什么 |
> |---|--------|-----------|
> | 1 | 候选人提到"做了一套东西把三个人的表格格式统一"，请让她具体描述这套东西的形态——是模板、脚本、还是文档规范？ | 改造是否真实存在，还是只是口头约定 |
> | 2 | 候选人称提示词"迭代了三四次"，请让她说出其中任意一次的具体修改内容和触发原因 | 迭代经历的真实性；能否说出细节 |
> | 3 | 候选人称"另外两个同事现在也在用"，请了解同事是主动来要的、她主动推的、还是领导要求的，以及同事是否做过修改 | 影响力的性质与真实程度 |

# 第4章 测评流程与业务规则

## 4.1 选择题设计（第0段）

固定5题，单页展示，全部必答，无对错，不计分。

| # | 题目 | 选项 | 用途 |
|---|------|------|------|
| Q1 | 过去一个月，你使用AI工具的频率大致是？ | 每天多次 / 每天一次 / 每周几次 / 偶尔 / 几乎不用 | 使用强度；追问种子 |
| Q2 | 你目前自己付费订阅的AI工具有哪些？（多选） | 列举5–6个主流工具 / 有但不在列表（填写）/ 没有付费订阅 | 主动投入程度 |
| Q3 | 你是否为自己或他人做过可复用的AI提示词模板、工作流或小工具？ | 从未 / 做过但只自己用 / 给过同事用 / 有人主动来找我要 | 定位L3/L4轨道；追问种子 |
| Q4 | 你身边的同事会来找你问AI相关的问题吗？ | 几乎不会 / 偶尔 / 经常 / 我是团队里主要的答疑人 | 影响力信号 |
| Q5 | 你最近一次因为AI给出的结果不准确而返工或纠正，是什么时候？ | 本周 / 本月 / 记不清了 / 没遇到过 | 核验意识的间接信号（"没遇到过"是危险信号，必追问） |

**注入规则**：Q1/Q3/Q5的选择结果必须注入考官模式上下文，并在Prompt中明确要求"针对候选人的自述进行验证性追问"。

## 4.2 考官模式阶段设计（第1段）

| 阶段 | 阶段目标（注入Prompt） | 最小轮次 | 最大轮次 | 触发条件 |
|------|---------------------|---------|---------|---------|
| **S1.1 开场校验** | 验证Q1自述的使用强度是否真实；获取至少1个具体的近期使用案例，包含：任务是什么、给了AI什么信息、AI输出后做了什么 | 3 | 5 | 必经 |
| **S1.2 核验意识** | 搞清候选人是否有主动核实AI输出的行为；是"每次都核""觉得不对才核"还是"基本不核"；核验的判断依据是什么；针对Q5追问具体案例 | 3 | 5 | 必经 |
| **S1.3 深度探测** | 搞清是否存在流程级改造、可复用资产、他人采纳、组织推动；每一项都要追到具体形态和细节 | 4 | 7 | 条件触发，见下 |

**S1.3 触发条件**（满足任一即触发）：
- Q3 选择"给过同事用"或"有人主动来找我要"
- Q4 选择"经常"或"我是团队里主要的答疑人"
- S1.1 或 S1.2 中，候选人主动提及流程改造、模板、工具、教别人、团队推广等内容（由大模型每轮输出的信号字段标记，见5.1）

**未触发S1.3的处理**：直接进入第2段。这本身就是一个判定信号——该候选人在L2及以下区间。

**时长控制**：第1段总时长上限15分钟。到达上限时，当前阶段完成本轮回答后立即结束，进入第2段。

## 4.3 工具模式设计（第2段）

**本期固定2个任务，全体候选人相同**（保证可比性）。

| # | 任务 | 时长 | 设计意图 |
|---|------|------|---------|
| T1 | **催收邮件**：一位合作两年的供应商逾期30天未交付，前两次沟通只回复"在处理"。请完成一封发给对方负责人的邮件，既要施加压力推动交付，又要保留后续合作可能。 | 12分钟 | 观测：是否主动补充背景、是否处理"施压/保关系"的张力、是否多轮迭代、修改指令是否具体 |
| T2 | **信息核查**：下面这段文字包含若干需要核实的事实性陈述。请判断哪些需要核实、如何核实，并给出你的处理结论。（附一段约200字、含2–3处可疑数据/断言的材料） | 8分钟 | 观测：核验意识是否落到行为、是否会指出AI也可能出错、是否要求AI提供依据 |

**规则**：
- T1 → T2 顺序固定，各自独立的干净上下文
- 每个任务候选人可主动点击"完成本环节"提前结束
- 时长到达自动进入下一环节
- 任务描述作为工具模式的首条内容展示，但**由系统卡片承载，不由AI说出**

## 4.4 等级定义与判定规则

### 等级定义

| 等级 | 核心特征 | 必要证据 |
|------|---------|---------|
| **L0** | 基本不使用AI，或使用但完全无法描述过程；对AI持排斥或盲目态度 | 无有效使用案例 |
| **L1** | 单轮问答式使用，把AI当搜索引擎；提示词简单无背景；几乎不迭代；无核验行为 | 有使用案例，但迭代≤1轮且无核验证据 |
| **L2** | 能拆解任务、提供背景；多轮有效迭代；有具体的核验案例（即使是被动触发） | 拆解证据 + 有效迭代 + 至少1个具体核验案例 |
| **L3** | 将AI嵌入工作流程，产生了可复用资产（模板/流程/工具）；有他人采纳的证据 | L2全部 + 流程级改造的具体形态 + 至少1个他人采纳案例，**且经现场验证** |
| **L4** | 组织级影响：主动推动他人/团队使用，有方法论沉淀，能评估他人的AI应用水平 | L3全部 + 组织级推动证据 + 方法论表述，**且经现场验证** |

### 轨道判定

| 轨道 | 特征 |
|------|------|
| **个人深度轨道** | 能力主要体现在自身应用的深度和复杂度 |
| **团队负责人轨道** | 能力主要体现在推动他人、评估他人、资源决策与落地组织 |
| **无法判断** | 证据不足 |

**说明**：轨道与等级是两个独立维度。一个L3的团队负责人轨道候选人，其L3证据可能主要来自"推动团队采纳"而非"个人深度改造"。

### 硬规则（约束大模型的判定自由度）

| 规则 | 内容 |
|------|------|
| R1 | **L3及以上必须有现场验证**。仅凭候选人环节，大模型最高只能输出"L3（待验证）"，不能输出确定的L3/L4 |
| R2 | **无原话证据不得下结论**。任一维度若无法引用候选人原话，该维度必须标记为"证据不足" |
| R3 | **自述不构成证据**。"我经常核验"不算核验证据，必须有具体案例（时间/对象/发现了什么/怎么处理） |
| R4 | **落差优先**。若自述水平明显高于实测表现，等级按实测表现判定，并单独标记落差 |
| R5 | **置信度低于0.6必须转人工**，无论等级高低 |

## 4.5 面试官环节触发条件

满足**任一**条件即触发（状态变为"待现场验证"）：

| # | 条件 | 理由 |
|---|------|------|
| 1 | 大模型初判为 L3（待验证）或 L4（待验证） | 高阶必须验证（R1） |
| 2 | 轨道判定为"团队负责人轨道" | 管理类能力必须现场验证 |
| 3 | 置信度 < 0.6 | 大模型自认判不准（R5） |
| 4 | 自述实测落差标记为"重大" | 需人工识别是夸大还是紧张 |
| 5 | 触发任一安全红线 | 需人工确认 |

**不触发**：L2及以下 且 置信度 ≥ 0.6 且 无落差/红线标记 → 状态直接置为"已完成"。

**触发判定函数**：上述 5 条件由后端 `shouldTriggerInterview` 函数实现（详见 architecture 4.3），评估A产出后立即调用；模型返回的 `recommend_human_review` 仅作辅助提示，不参与触发决策。

## 4.6 安全红线

红线**不参与等级判定**，独立标记并强制转人工。

| # | 红线 | 判定依据 |
|---|------|---------|
| RL1 | **无边界的数据使用**：描述中出现将客户信息、内部未公开数据、个人敏感信息直接提供给公网AI，且无任何风险意识表述 | 对话中的具体描述 |
| RL2 | **零核验交付**：将AI输出未经任何核验直接对外交付，且已造成实际问题但无反思 | 对话中的具体案例 |
| RL3 | **明确的虚构**：前后陈述矛盾，或追问细节时表述崩塌（如称"迭代了多次"但完全说不出任何一次改了什么） | 对话内部矛盾 + 追问结果 |
| RL4 | **绝对信任**：明确表示AI输出无需核验、AI不会出错 | 直接表述 |

## 4.7 异常规则（本期从简）

| 异常 | 处理 |
|------|------|
| 候选人中途关闭页面 | 视为放弃，状态置为"已放弃"。面试官可点击"重新生成链接"让候选人重做（从头开始，不续答） |
| 候选人长时间无响应 | 单轮无输入超过5分钟，前端提示；超过10分钟，该阶段自动结束进入下一阶段 |
| 大模型接口失败（对话/工具模式） | 前端重试3次；连续失败展示"系统繁忙，请稍后重试"，保留已有日志，候选人可刷新继续当前阶段 |
| 评估A失败 | 后台记录失败，状态置为"评估失败"，提供"重新评估"按钮。面试官可调 `scope=all` 或 `scope=evaluation` 重试 |
| 终判C失败 | 状态从"终判中"回退至"评估失败"，A仍锁定不展示（B已锁定不可改）。面试官可调 `scope=evaluation` 重试终判，不重跑题纲 |
| 题纲生成失败（黑名单3次重试均命中） | 题纲置 null，降级为"仅展示原始日志"，不阻断评估A；面试官侧报告页提示"题纲生成失败" |
| 面试官粘贴的记录过短 | 少于200字时弹窗确认"记录较短，是否确认提交"，但不阻断提交 |

## 4.8 状态机

**测评状态**：

```
未开始 ──候选人打开链接──▶ 进行中 ──提交──▶ 评估中
                              │                 │
                              │            ┌────┴────┐
                        中途关闭         不触发      触发
                              │            │         │
                              ▼            ▼         ▼
                          已放弃       已完成    待现场验证
                                                     │
                                          面试官提交B│
                                                     ▼
                                                  终判中
                                                     │
                                                     ▼
                                                  已完成
```

**PoC阶段不做**：暂停、超时自动放弃、重测计数、状态回退。

## 4.9 大模型判定与面试官判定的关系

**本期不做加权合成。**

- 系统并列展示 A / B / C 三个结论
- 系统自动计算并落库一致性标记：`A=B?` `B=C?` `A=C?` `最大等级差`
- 不产生"最终唯一等级"字段

**理由**：PoC的目的是测量两者的差异。一旦加权合成，差异就被抹平，H2/H4无法验证。权重设计留待验证之后。

# 第5章 大模型能力设计

本章为开发核心依据。所有Prompt以配置文件形式管理，产品团队可直接修改，不做管理界面。

## 5.1 考官模式 Prompt 设计

### 输入上下文构成

```
[System Prompt：考官模式基础设定]
+ [候选人选择题结果（结构化）]
+ [当前阶段目标]
+ [本阶段对话历史]
```

**注意**：跨阶段时，前序阶段的对话历史**保留**（考官模式内部连续），但工具模式**完全隔离**。

### System Prompt 要点

```
你是一个AI素质测评的对话考官。你的任务是通过对话，采集候选人真实的
AI使用行为信息。

【本阶段目标】
{{stage_goal}}

【候选人自述信息】
{{questionnaire_result}}
说明：以上是候选人的自我报告，可能存在美化。你的重要任务之一是通过
追问具体细节来验证这些自述。

【提问原则】
1. 一次只问一个问题，问题要短，口语化
2. 优先追问具体细节：具体做了什么、给了AI什么信息、结果如何、然后
   做了什么。不要问抽象的看法、感受或观点
3. 当候选人给出笼统回答（如"效果不错""我会核实的"）时，必须追问具体
   案例：什么时候、什么事、具体怎么做的
4. 当候选人的回答与其自述不一致时，不要指出矛盾，继续自然追问细节
5. 保持中立自然的对话语气

【严格禁止】
- 不得透露任何评分标准、等级体系、维度名称
- 不得评价候选人回答的好坏（不说"很好""不错""这个思路很棒"）
- 不得给出提示、建议或引导性的示范
- 不得安慰或鼓励
- 不得询问与AI使用无关的话题
- 不得宣布环节结束或提示进入下一环节（由系统控制）

【输出格式】
严格输出JSON：
{
  "question": "你要向候选人说的话",
  "signals": {
    "goal_coverage": 0.0-1.0,          // 本阶段目标的信息采集完成度
    "mentioned_process_change": true/false,  // 是否提及流程级改造
    "mentioned_asset": true/false,           // 是否提及可复用资产
    "mentioned_others_adoption": true/false, // 是否提及他人采纳
    "mentioned_team_driving": true/false,    // 是否提及团队推动
    "answer_vagueness": 0.0-1.0        // 上一次回答的笼统程度
  }
}
```

### 后端使用 signals 的规则

| 用途 | 规则 |
|------|------|
| 阶段推进 | `goal_coverage ≥ 0.8` 且已达最小轮次 → 推进下一阶段 |
| S1.3触发 | 任一 `mentioned_*` 为 true → 标记触发S1.3 |
| 强制追问 | `answer_vagueness ≥ 0.7` → 本阶段最大轮次 +1（上限内） |

**再次强调**：signals 只是输入，推进决策由后端状态机做出。

## 5.2 工具模式 Prompt 设计

### 输入上下文构成

### System Prompt

```
你是一个通用AI助手。请正常、专业地响应用户的请求。

- 不得主动询问用户的背景信息、目标或约束条件。用户给了什么信息，你就
  基于什么信息完成任务
```

- 前端类型由 OpenAPI 生成，全部使用 camelCase

## 5.5 追问题纲生成 Prompt

**输入**：候选人环节完整日志（不含评估结果）

**输出**：

```json
{
  "questions": [
    {
      "index": 1,
      "quote": "做了一套东西把三个人的表格格式统一",
      "ask": "请让她具体描述这套东西的形态——是模板、脚本、还是文档规范？",
      "verify": "改造是否真实存在，还是只是口头约定"
    }
  ]
}
```

**硬约束**：

| 约束 | 内容 |
|------|------|
| 数量 | 3–5条 |
| 必须引用原话 | 每条必须有 `quote` 字段，来自候选人原话 |
| 禁止通用问题 | 不得生成"请谈谈你的AI使用经验"这类不依赖候选人具体表述的问题 |
| **禁止泄露判定** | 输出中不得包含等级、分数、评分维度名称、"该候选人可能达到L3"等任何倾向性表述 |
| 指向验证 | 每条必须说明"想验证什么" |

**开发注意**：这个Prompt与评估Prompt必须是**两次独立调用**，且题纲生成的输入不包含评估结果。这是为了保证面试官看到的题纲不受初判污染。

| 初判详情区 | A的完整内容（折叠） |
| 面试官判断区 | B的等级、轨道、理由 |
| 面试记录区 | 面试官提交的文字记录全文（折叠） |
| 原始日志区 | 同上 |

# 第8章 验证方案与验收标准

## 8.1 测试对象

| 项 | 要求 |
|----|------|
| 数量 | 12–15人 |
| 来源 | 内部员工 |
| 关键要求 | **面试官对其AI实际水平有真实了解**（共事过、见过其工作产出） |
| 分布要求 | 需覆盖各等级：L0–L1约3人、L2约5人、L3约4人、L4约1–2人；其中至少3人为团队负责人角色 |
| 招募说明 | 明确告知这是产品验证，非考核，结果不进入绩效 |

**为什么不用真实候选人**：题目质量尚未标定，且H3的验证依赖"面试官了解其真实水平"，真实候选人无法提供这个参照。真实场景验证放在PoC之后。

## 8.2 实验流程（必须严格遵守）

```
第1步  面试官在系统外，先对每位测试对象独立填写"预期等级"
       （写在系统之外的表格中，不进入系统，避免影响后续）
第2步  测试对象完成测评
第3步  系统产出 A
第4步  对触发面试官环节的对象，面试官按题纲现场提问、录入记录
第5步  面试官提交 B（此时仍未看到A）
第6步  系统产出 C
第7步  展示三方对比，面试官记录主观感受
第8步  产品团队汇总：预期等级 / A / B / C 四方对比 + 全部日志人工阅读
```

**第1步的"预期等级"是本PoC的地面真值（ground truth）参照**，必须在测试对象作答之前完成，且不得进入系统。

## 8.3 验收标准

### 功能验收

| # | 标准 |
|---|------|
| F1 | 场景1、2、3能完整走通，无阻塞性缺陷 |
| F2 | 工具模式上下文完全隔离，经抽查确认AI未表现出"知道这是测评" |
| F3 | 面试官在提交B前，页面上无任何途径可见A的等级结论（含列表页、接口返回） |
| F4 | 追问题纲不含等级、分数、维度名称等泄露性表述 |
| F5 | 所有日志（含Prompt全文与模型原始返回）完整落库可导出 |

### 假设验收

| 假设 | 验收标准 |
|------|---------|
| **H1** | ① 大模型输出中，"证据不足"维度占比 ≤ 20%<br>② 人工阅读日志后判断"信息量足以支撑等级判定"的比例 ≥ 80%<br>③ 不同预期等级的候选人，日志在长度、迭代轮次、细节丰富度上呈现可辨识的差异 |
| **H2** | ① A 与 预期等级 的一致率 ≥ 70%<br>② A 与 B 的一致率 ≥ 70%<br>③ 相差2级及以上的案例 ≤ 10% |
| **H3** | ① 工具模式行为特征（提示词完整度、迭代轮次、修改具体性）与面试官对其日常表现的了解相吻合的比例 ≥ 70%<br>② anomaly_signals 的误报率可接受（人工复核确认） |
| **H4** | ① 面试记录可用（关键内容清晰、说话人可辨）的比例 ≥ 90%<br>② C 与 B 的一致率 ≥ 70%<br>③ C 与 B 的一致率 **高于** A 与 B 的一致率（证明面试官环节有增量价值） |

### 附加观察指标（不设阈值，仅记录）

| 指标 | 用途 |
|------|------|
| 平均测评时长 | 判断30分钟设定是否合理 |
| 各阶段实际轮次分布 | 判断轮次上限设置是否合理 |
| S1.3 触发率 | 判断深度探测触发条件是否过松/过紧 |
| 面试官环节触发率 | 判断人工介入成本是否可接受 |
| 置信度分布 | 判断大模型是否存在系统性的置信度虚高/虚低 |
| 红线触发情况 | 判断红线定义是否过于严苛或形同虚设 |

## 8.4 失败也是结果：必须产出的失败案例分析

**如果指标未达标，本PoC的产出不是"失败"，而是以下诊断结论。** 必须逐案分析每一个不一致案例，归因到下表之一：

| 归因类别 | 典型表现 | 对应的改进方向 |
|---------|---------|--------------|
| **A. 阶段目标设计问题** | 大模型问不到关键信息，或问题偏离目标 | 修改阶段目标定义与轮次配置 |
| **B. 考官Prompt问题** | 追问不深入、被笼统回答带过、泄露倾向 | 修改考官Prompt |
| **C. 工具任务设计问题** | 任务无法区分不同水平，所有人表现相似 | 重新设计实操任务 |
| **D. 评估Prompt问题** | 证据引用正确但等级映射错误、置信度不合理 | 修改评估Prompt与等级定义 |
| **E. 等级定义问题** | 等级边界模糊，面试官自己也难以判断 | 重新定义等级与必要证据 |
| **F. 产品形态问题** | 对话形式本身无法采集到关键信息，需要其他形式 | **重新考虑产品形态**（最严重的结论） |

**判断优先级**：先排除 B/D（Prompt问题，改起来最便宜），再看 A/C（设计问题），最后才考虑 E/F。

**F类结论的判断标准**：如果在 B/D 已经多轮调优后，A与预期等级的一致率仍低于50%，且人工阅读日志后认为"这些日志本身就无法判断这个人的水平"，则应判定为形态问题，PoC结论为"对话式测评不足以支撑AI素质判定"，需回到方案设计阶段。

## 8.5 PoC结束后的决策点

| 结论 | 下一步 |
|------|--------|
| 全部达标 | 进入真实候选人小规模试点，补齐通知、管理、报告导出等功能 |
| H1/H2达标，H4未达标 | 保留候选人环节自动化，重新设计面试官环节（考虑结构化表单替代文字记录） |
| H3未达标 | 工具模式设计需重做，考虑更长的实操任务或真实工作环境观测 |
| H2严重未达标（<50%） | 按8.4归因分析，判断是Prompt迭代还是形态重做 |

## 附录C 开发注意事项汇总（最容易做错的点）

| # | 事项 | 风险 |
|---|------|------|
| 1 | 工具模式上下文必须完全干净 | 直接导致H3无法验证 |
| 2 | 提交B前必须彻底隐藏A（包括接口返回，不能只是前端不显示） | 直接导致H2/H4数据作废 |
| 3 | 追问题纲与评估是两次独立调用，题纲输入不含评估结果 | 题纲会泄露判定倾向 |

| 5 | 所有Prompt全文与模型原始返回必须落库 | PoC分析无据可依 |
| 6 | 切换环节后视觉上清空历史 | 模式边界不清，候选人行为失真 |
| 7 | 采集阶段不做语义判断（不标记"有效迭代"等） | 固化未验证的假设 |
